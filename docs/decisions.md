# Decisions beyond the architecture doc

Choices made where `docs/architecture.md` is silent. Newest at the bottom. Each entry: what,
why, and the PR that introduced it.

| # | Decision | Why | PR |
|---|---|---|---|
| 1 | Runtime-checked sqlx queries (`query_as::<_, T>`) instead of the compile-time macros the doc mentions. | `.sqlx` offline data conflicts on every rebase of a stacked PR; integration tests against real Postgres give the same safety. | 01 |
| 2 | Errors render as `{ "error": { "code", "message" } }` (`application/json`) with the matching HTTP status; `code` is a stable snake_case identifier. | One shape for every failure; clients switch on `code`. | 01 |
| 3 | IDs are UUID v7 generated in Rust. | Time-ordered (good index locality, usable as pagination cursor); PG16 has no native v7. | 01 |
| 4 | Single integration test binary (`tests/it`) with modules. | One link step instead of one per file. | 01 |
| 5 | Tenant-scoped queries run as `courtpit_app` (NOLOGIN, NOBYPASSRLS, not a table owner) via `SET LOCAL ROLE` inside `TenantTx`; the pool's login role owns the schema and is granted `courtpit_app`. Policies use `app_current_community()` = `nullif(current_setting('app.community_id', true), '')::uuid`. | One pool; RLS can't be bypassed by the owner role on the scoped path; an unset or reset GUC yields no rows instead of a cast error. Production: the migrating/login role needs `CREATEROLE` once (or create `courtpit_app` out of band) and must be granted `courtpit_app`. | 02 |
| 6 | Integration tests clone a per-test database from a template migrated once per process (`courtpit_tpl_<hash of migrations>`, built under an advisory lock and renamed into place); stale test DBs are dropped at harness start. | Isolation of a fresh DB at the cost of a file copy rather than a full migration per test. | 02 |
| 7 | `users.email` is unique case-insensitively (`lower(email)` index). `player_status` adds `deleted` for self-service account deletion (anonymise, keep match history consistent). Tenant parents also carry `UNIQUE (community_id, id)` so children can use composite FKs that pin them to the same community. | Spec silent. | 02 |
| 8 | Tenant resolution order: `X-Courtpit-Community` header, then Host `{slug}.{COURTPIT_BASE_DOMAIN}` (single label only), then Host as a registered `custom_domain`. Missing → 400, unknown → 404. Resolved communities are cached 60 s (moka); misses are not cached. | Header for native builds, host for web; short TTL lets branding edits propagate without invalidation plumbing. | 03 |
| 9 | Signing in through a community's app (OTP, password, OIDC) creates the player membership in that community (open join policy). A session is global; `CurrentPlayer` rejects requests to communities the user hasn't joined (403) and banned members (403). | Spec: identity vs membership; resolves "how does a user become a player". | 05 |
| 10 | Session delivery: body token by default (native); `X-Courtpit-Client: web` gets an `HttpOnly; SameSite=Lax; Secure` cookie and no token in the body. Both are accepted on every request. | Token in a web JS body would defeat httpOnly. | 05 |
| 11 | OTP rules: 6 digits, SHA-256(code_id ‖ code) at rest, 10-minute expiry, 5 wrong guesses burn the code, a new request invalidates older codes, ≤5 codes per address per hour (DB-counted), and per-IP limits on request/verify/login (in-memory `governor` GCRA: a burst of `COURTPIT_AUTH_IP_LIMIT_PER_HOUR`, refilled evenly over the hour); the client IP comes from `COURTPIT_CLIENT_IP_SOURCE` via `axum-client-ip` (default `ConnectInfo`; behind a proxy, its header such as `FlyClientIp` or `RightmostXForwardedFor`, never the spoofable leftmost `X-Forwarded-For` entry). Always 202 on request (no account enumeration). | Spec says "hashed, rate limited"; these are the concrete numbers. In-memory limits are per instance, acceptable at expected scale. | 05 |
| 12 | Passwords: argon2id defaults via `password-auth`, 10–256 chars, settable by any authenticated session (the emailed code is the proof), so "forgot password" is just OTP sign-in + set. Password login requires a verified email. | Keeps one recovery path. | 05 |
| 13 | Email is sent inline from the request in this step; moving it onto the job queue is deferred to the notifications step. | Jobs land in PR 11; OTP latency matters more than retries for now. | 05 |
| 14 | OIDC account linking: an existing `(provider, subject)` identity wins; otherwise a *verified* provider email links to the account with that email; an *unverified* provider email matching an existing account is refused (409) to prevent takeover; otherwise a new user is created. Signed-in users can link explicitly via `POST /auth/oidc/{provider}/link`. JWKS cached 1 h, refetched once on unknown `kid`; RS256 only; 60 s leeway. | Spec says "verify ID tokens"; linking policy is ours. | 06 |
| 15 | Account deletion anonymises instead of hard-deleting: all memberships become "Deleted player" with personal fields cleared and status `deleted`; identities, codes and sessions are deleted; the email is replaced by `deleted+<id>@deleted.invalid`, freeing the address. Export and delete read/write the user's own rows across communities via the pool (privileged path) with an explicit `user_id` filter. | Match history references player ids in arrays; anonymising keeps it consistent. | 07 |
| 16 | Input extractors `ApiJson`/`ApiQuery`/`ApiPath` turn axum rejections into the standard error JSON (body data errors → 422, syntax/shape → 400). `PATCH` bodies distinguish absent from `null` (clears the field) and reject unknown fields. UTR and other decimals are JSON numbers. | Consistent error shape for clients. | 07 |
| 17 | Directory: lists only `active` members with a verified email, excludes the caller, `play_pref=singles|doubles` also matches `any`, `location` is a case-insensitive substring over `preferred_locations`, cursor = last player id. Phone/socials appear only if the player opted in *and* the viewer is verified; gender is never serialised outside `/me`. | Spec §11/§18; filter semantics are ours. | 08 |
| 18 | Admin moderation: admins can ban/unban players; only owners can moderate admins; nobody can moderate themselves or an owner. | Spec says "admin ban/remove"; hierarchy is ours. | 08 |
| 19 | Match FSM details: proposals (and accepting a new one) are allowed while `proposed` *or* `scheduled` (rescheduling); declining a single proposal leaves the match open, cancelling it is a separate event; walkovers are admin/system only (a player can't claim a no-show); players may cancel friendlies but only admins cancel competitive matches; admin `replay` sends a disputed match back to `scheduled`, `void` to `cancelled`. | The spec diagram leaves these edges implicit. | 10 |
| 20 | `tiebreak_at` must equal `games_per_set` (or be absent for advantage sets); a pro set uses the format's tiebreak setting at 8–8; a match tiebreak counts as one game in game totals. | Keeps validation total and unambiguous; covers the formats the spec lists. | 09 |
| 21 | Jobs use claim-with-lease rather than holding a row lock for the job's duration: `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` sets `locked_at`; a lease older than 5 min is reclaimable (crashed worker). Success sets `completed_at` (rows are kept for audit); failure clears the lease, records `last_error`, and retries after `min(2^attempts, 3600)` s until `max_attempts` (10) sets `failed_at`. Unknown `kind`s are retried, not dropped. Each handler runs in its own task so a panic fails the job, not the loop. An optional `dedupe_key` keeps at most one *waiting* (unclaimed) job per key; re-enqueueing reschedules it, a running job may enqueue its successor under its own key, and a failed run whose successor is already waiting is marked superseded instead of retried. | No long transactions across handler IO; safe for several instances. | 11 |
| 22 | An injectable `Clock` (`SystemClock` in production, `OffsetClock` = wall time + adjustable offset in tests) lives on `AppState`; the job loop claims with `run_at <= clock.now()`. | Season transitions and confirmation deadlines are tested by advancing the clock instead of sleeping or rewriting rows; at offset 0 it agrees with the database clock. | 11 |
| 23 | Friendly matches are visible to their players and admins only; league (competitive) matches to every member. `GET /matches` lists your own matches newest first; `league_id=` lists a league's; `all=true` (admins) lists everything. Friendly mixed matches do not check gender (eligibility rules apply to league entries). | Friendlies are private arrangements; league schedules are public within the club. | 12 |
| 24 | Admins referee matches through `/admin/matches/*`; an admin who plays in the match may not referee it (the owner may, so a one-admin community is never stuck). | Conflict of interest. | 12 |
| 25 | Scheduling is only by proposal: at most one is open per match; a counter-proposal (or cancelling the match) marks the open one `superseded` (an extra `proposal_status` value); accepting sets `scheduled_at`/`location`. Proposed times must be in the future and within a year; a proposal whose time has passed can't be accepted. | One open proposal keeps the flow unambiguous without chat. | 13 |
| 26 | Results: only a `scheduled` match can be reported (accept a proposal first). Reporting sets `confirm_deadline_at = now + settings.confirm_window_days` (default 3, clamped 1–30) and enqueues an `auto_confirm_match` job (dedupe key per match) at the deadline; the job is a no-op unless the match is still `reported` and due. Disputes record `disputed_by`/`dispute_note`; admin `replay` clears the report so it can be reported again; walkovers store `winner_side` with a null score. | Spec §8; a no-op-safe job tolerates retries and re-reports. | 14 |
| 27 | Match requests: `slots_open` counts players still needed (singles 1; doubles 3, or 2 when the creator names a `partner_id`). Joining checks the UTR band (players without a UTR can't join banded requests), locks the request row and, on the last slot, creates a friendly match: participants ordered creator, partner, joiners by join time, first half = side A (so without a partner the creator plays with the first joiner). The match starts `proposed` with the creator proposing the window start (if still ahead). Requests whose window has ended are hidden and unjoinable (no job needed). `match_request_joins` carries `community_id` for RLS. | Spec §11 leaves sides and expiry open. | 15 |
| 28 | Division placement: box count = the one whose balanced sizes stray least outside `min_size..=max_size` (default 6–8), ties to fewer boxes. Entries are ordered by an effective tier — last season's tier moved by promotion/relegation for returning entries, the UTR-only tier for newcomers — then UTR (unknown last), then id, and cut into boxes, tier 1 on top. Round robin uses the circle method with a bye for odd counts and alternating sides. Single-elimination draws pad to the next power of two with byes to the top seeds, standard bracket positions (1 v N, seeds 1/2 in opposite halves). | Spec §9/§10: "boxes of 6–8", deterministic, promotion/relegation applied next season. | 16 |
| 29 | Scoring: `ScoringConfig` mirrors the spec JSON with every field defaulted and unknown keys rejected, so a league's `scoring_overrides` is deep-merged over the community config and then parsed. Season points = `round(position_points[pos] × tier_multiplier[tier])`, tiers past the table use the smallest multiplier, positions past it get 0. Tournament points = `base(draw) × pct / 100` rounded half up, `base` taken from the largest listed draw size ≤ the draw (else the smallest). Standings order: points, wins, set diff, game diff, entry id (no head-to-head in v1); walkovers count as played with no sets/games. | Spec §12 gives values, not rounding/fallback rules. | 17 |
| 30 | Leagues are created as unpublished drafts (admins only see them, and only drafts are editable). `POST /admin/leagues/{id}/publish` stamps `published_at` and opens registration immediately if `registration_opens_at` has passed; afterwards the dates drive the status (lifecycle job). Registration is open while `status = registration` and `opens_at <= now < closes_at`. Leagues carry `box_min_size/box_max_size` (default 6–8) and an optional `previous_league_id` whose promotion/relegation seeds placement. Cancelling a league cancels its unplayed matches. | Spec §9 says the dates drive the lifecycle but not how a league goes public. | 18 |
| 31 | Registration: one live (non-withdrawn) entry per player per league, enforced under a lock on the league row (arrays can't carry a unique constraint). Singles confirm at once (no fees yet; `pending_payment` reserved). Doubles/mixed entries start `pending_partner` with an `invited_partner_id` (an extra column) or `looking_for_partner`; accepting confirms the entry and withdraws the accepter's own solo entries; declining clears the invite. Mixed eligibility (one female + one male; other/undisclosed ineligible) is checked on invite, on accept and on admin pairing, with a message saying why. Players withdraw while registration is open; admins until the league ends. The invited partner is shown only to the entry's players, the invitee and admins. | Spec §9; concrete rules are ours. | 19 |
| 32 | Ranking ledger: a league match reaching a result (confirmed, auto-confirmed, resolved with a score, walkover) appends one `ranking_events` row per player in the same transaction, `occurred_at` = when the result was recorded, idempotent via `UNIQUE (source, source_id, player_id)`. Friendly matches write none. Events keep the discipline played; the refresh applies `mixed_pooling` (so changing it needs no ledger rewrite) and sums `occurred_at ∈ (now − 52 weeks, now]` for active players, `rank()` so ties share a rank. The `refresh_rankings` job runs after new events and re-enqueues itself daily so points decay without new results. `GET /rankings/events?player_id=` exposes the ledger (audit). | Spec §12 "ledger, not a computed field". | 20 |
| 33 | League lifecycle runs as one self-rescheduling `advance_league` job per league (dedupe key per league), enqueued on publish. Each run applies every due step at `clock.now()` (a late run catches up) and re-enqueues at the next date. Activation at `starts_at`: incomplete entries (`pending_partner`/`pending_payment`) are withdrawn, confirmed entries are placed with the domain placement (pairs by mean UTR), one `league_divisions` row per box ("Box n", tier, actual UTR band), and every box's round robin becomes `proposed` league matches (sides copied from the entries, round numbered from 1, the league's format) that players self-schedule. | Spec §9; "no mid-season jobs". | 21 |
| 34 | Season end (`ends_at`): unplayed (`proposed`/`scheduled`) league matches are cancelled ("season ended"); matches still `reported`/`disputed` don't count for the final table (they may still earn match points later). Final standings are stored in a `league_results` table (position, points, season points, movement −1/0/+1, player_ids); promotion/relegation is top two up / bottom two down, none above tier 1 or below the bottom tier, capped at half a box. Season points (each partner in full) go to the ledger as `league_season` events. A league naming `previous_league_id` seeds returning players — or unchanged pairs — from those results. Standings (`GET /leagues/{id}/standings`) are always computed live from results. | Spec §9/§12 leave the storage and edge cases to us. | 22 |
| 35 | `MatchFormat.deuce` is `advantage` (default) or `golden_point` (no-ad: the point at 40–40 decides the game; tiebreaks stay win-by-two). It is stored and shown but never affects validation, since scores are reported per set, not per point; formats stored without the key read as `advantage`. | Golden point is common in club and league tennis; making it a format attribute needs no migration and keeps validation unchanged. | 09 |
| 36 | `courtpit-server tick` drains due jobs and exits: it takes `serve`'s flattened `Config` (jobs may send email) plus `--max-seconds` (`COURTPIT_TICK_MAX_SECONDS`, default 300), opens no HTTP listener and calls `jobs::tick`. The budget only gates *starting* a job: jobs are claimed one at a time right before they run, so running out of budget can never leave a claimed job under a lease (nothing to release, no attempt burned). A handler already running is awaited to the end, not cut off: cutting it off would leave half-done side effects that the retry repeats, so a long job can overrun the budget (the host's stop timeout is the hard cap). The tick logs `ran` and `budget_spent` and exits 0 whenever it could use the database; a job that fails is recorded and retried as usual and does not affect the exit code, while a database error exits non-zero. Claiming is the unchanged `SKIP LOCKED` + lease, so a tick is safe next to a live `serve`. | Phase-1 hosting stops the Machine when idle, so nothing polls `jobs`; a scheduled Machine runs `tick` hourly. | 23 |
| 37 | The S3 client is hand-written (`backup::s3`) rather than `aws-sdk-s3`: SigV4 header signing needs only `hmac` (new, tiny) on top of the `reqwest` and `sha2` already used, plus `percent-encoding` (already in the tree), against roughly 100 extra crates (aws-smithy, aws-config, ...) and their compile time for six calls. It uses path-style URLs, multipart upload in 8 MiB parts (the dump length is unknown; every part but the last must be at least 5 MiB), `AbortMultipartUpload` on any failure, and treats a 200 with an `<Error>` body on completion as a failure. XML is read by hand (four tags plus entity decoding, safe because S3 escapes `<` in text) instead of adding `quick-xml` for a few lines. Signing is tested against AWS's published GET Object and List Objects examples, and a fake S3 server re-derives each request's signature. The client sits behind the `ObjectStore` trait so tests can use an in-memory fake. | Smallest dependency footprint that is provably correct without network access. | 23a |
| 38 | `jobs::enqueue_if_absent` inserts a job only when no unfinished job (waiting *or running*) exists under its dedupe key, and never touches an existing one; `enqueue` still replaces the waiting job's time. A job that failed for good leaves no unfinished row, so the next start creates it again. | Bootstrapping a self-rescheduling job on every start and hourly tick with `enqueue` (`ON CONFLICT DO UPDATE`) would push its run time forward forever; counting a running job stops a start from queueing a second run while one is in flight. | 23b |
| 39 | Nightly backup is the self-rescheduling job `backup_database {}` (dedupe key `backup`): dump, upload, prune, then enqueue the next run at the next `BACKUP_HOUR_UTC` (default 3) strictly after the job's start. The successor is enqueued only after success, so a failure is retried with the normal backoff (about 17 minutes over 10 attempts) instead of being superseded until tomorrow; if the retries run out, the next `serve`/`tick` start re-creates the job. `serve` and `tick` call `backup::ensure_scheduled` on start (insert-if-absent, first run at the next `BACKUP_HOUR_UTC`). Backups are enabled iff `BACKUP_S3_ENDPOINT`, `_BUCKET`, `_ACCESS_KEY` and `_SECRET_KEY` are all set (blank counts as unset); some but not all is a startup error naming the missing ones, and with none the job is a logged no-op that completes. The dump uses `BACKUP_DATABASE_URL`, which must be the direct (non-pooled) URL on Neon because `pg_dump` cannot run through transaction pooling; it falls back to `DATABASE_URL`. | An hourly `tick` can only run what is due, so the schedule lives in the jobs table like every other timer. | 23b |
| 40 | The dump is `pg_dump --format=custom --no-owner --no-privileges`, read as a stream from its stdout. The password travels in `PGPASSWORD` and the user in `PGUSER`; the rest of the URL (host, database, `sslmode`, ...) is passed as `--dbname`, so no secret is on the command line. A non-zero `pg_dump` exit is reported as a read error at the end of the stream, so the upload is aborted instead of completing a truncated dump, and the job fails with pg_dump's stderr (truncated to 1000 characters). Dropping the stream kills `pg_dump`. The source sits behind a `DumpSource` trait so job tests use a fake instead of a `pg_dump` binary. A missing binary fails the job with "pg_dump not found: the image must include postgresql-client". | A dump that looks complete but is not is worse than none; secrets stay out of `ps`. | 23b |
| 41 | Object keys are `{BACKUP_S3_PREFIX}{YYYY}/{MM}/courtpit-{YYYYMMDDTHHMMSSZ}.dump` (prefix normalised to end in `/`), the timestamp being `clock.now()` at job start. Pruning runs only after a successful upload and deletes objects under the prefix whose *key-encoded* time is before `now - BACKUP_RETENTION_DAYS` (default 14, at least 1); a key counts as ours only if it round-trips exactly through the key format under the prefix, so foreign, unparseable or differently laid-out objects are never deleted. A failed prune is logged and does not fail the job (the retry would upload a second dump); the next night prunes again. | Object modification times can be touched by other tools; the key is ours and never changes. | 23b |
| 42 | The backup job runs under the normal 5-minute lease. A dump that takes longer could be claimed by another worker (for example a live `serve` loop while a tick is still dumping) and start a second dump; that is harmless (distinct timestamped key, both complete, both prune) so the lease is not extended per kind. | Per-kind leases would complicate the claim query for a harmless duplicate; revisit if dumps routinely exceed 5 minutes. | 23b |
| 43 | The server image is multi-stage: `rust:1.99-slim-trixie` builder (any Rust ≥ the workspace's 1.88; pinned to a minor) with cargo-chef caching, then `debian:trixie-slim` with `ca-certificates`, a non-root user (uid 10001) and PGDG's `postgresql-client-18`. `CMD ["courtpit-server", "serve"]`, no `ENTRYPOINT`. This replaces the spec's "distroless" image. | The nightly backup shells out to `pg_dump`, which must be at least the server's major version. Neon creates Postgres 18 projects by default (14–18 supported); Debian trixie ships 17 and bookworm 15, so the client comes from the PGDG apt repo, and a newer client dumps every older server. Bump `PG_MAJOR` when Neon's default moves. No `ENTRYPOINT` lets Fly's `release_command` and `fly machine run … courtpit-server tick` replace the command. | 24 |
| 44 | The hourly `courtpit-server tick` runs on a Fly scheduled Machine created once with `fly machine run --schedule hourly --restart no --metadata courtpit_role=tick …`, not from `fly.toml`. After every deploy the workflow finds it by that metadata and runs `fly machine update <id> --image <web image> --env COURTPIT_*=… --skip-start --yes`. | `fly.toml` has no schedule key (its process groups are always-on Machines), and `fly deploy` only updates Machines carrying `fly_platform_version=v2` (flyctl source), so it never touches or re-images a `machine run` Machine. `machine update` keeps the schedule. `fly machine run` does not read `fly.toml`'s `[env]`, so the workflow copies the `COURTPIT_*` values; secrets reach every Machine anyway. `--restart no`: a failed run waits for the next hour; leased jobs are re-claimed. | 24 |
| 45 | Deploys run from `.github/workflows/deploy.yml` on `workflow_run` of CI on `main` (success, `push` event, same repository), or by hand from `main`. | 46 | Phase 1 sizing in `fly.toml`: `shared-cpu-1x` with 512 MB, request concurrency 25 soft / 50 hard, `COURTPIT_DB_MAX_CONNECTIONS=5`, `COURTPIT_JOB_POLL_MS=5000`, `kill_signal=SIGTERM`, `kill_timeout=15`, and an HTTP check on `/healthz` only. | 256 MB is tight for bursts of argon2id hashing (about 19 MiB each); Neon's pooler multiplexes, so a small pool suffices; the job loop only polls while the Machine is awake and the tick covers the rest; `/readyz` queries the database, so using it as a check would wake Neon on every probe. | 24 |
| 47 | `fly.toml`'s `[env]` holds only non-secret `COURTPIT_*` settings. | 48 | Neon: the first migration runs as Neon's default role, which is in `neon_superuser` and so has `CREATEROLE`, so no out-of-band step is needed; a role made with plain SQL lacks it and needs `courtpit_app` created by `neondb_owner` first.
